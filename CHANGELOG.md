## [0.45.0](https://github.com/yackey-labs/yauth/compare/v0.44.0...v0.45.0) (2026-08-23)


### ⚠ BREAKING CHANGES

* **middleware:** a rate-limited request now answers 429 with Content-Type: application/problem+json and the body {"title":"Too Many Requests","status":429,"detail":"rate limit exceeded","retry_after":N} instead of text/plain "Too Many Requests". Retry-After and the X-RateLimit-* headers are unchanged. Act if you string-compare the 429 body against "Too Many Requests", surface it to users as prose, or log it expecting text; switch to the status code, or to `detail`. Clients that already parse problem+json — including yauth's own TS client — need no change and get a better message. Clients that call JSON.parse before checking response.ok stop erroring on this path.

## [0.44.0](https://github.com/yackey-labs/yauth/compare/v0.43.0...v0.44.0) (2026-08-15)


### ⚠ BREAKING CHANGES

* **yauthcfg,yauth:** yauthcfg.PluginsConfig gains an AuditExport field. The loader runs with KnownFields(true), so a yauth.yaml carrying plugins.audit_export previously failed to boot and now configures the plugin — no existing config changes meaning, but a Go caller constructing PluginsConfig as a positional struct literal will not compile.
* **ssosaml:** on a deployment issuing Secure cookies, /sso/saml/login now sets a short-lived SameSite=None binding cookie and /sso/saml/acs refuses an SP-initiated response presented without it (HTTP 400). A deployment that terminates the ACS on a different site than the one that served /sso/saml/login, or that strips cookies at a proxy, must set ssosaml.Config.LoginStateBinding to "off". Plain-HTTP deployments are unaffected by default: "auto" binds only when the deployment already issues Secure cookies.
* **ssooidc,oauth,mfa,ci:** an ssooidc deployment whose IdP JWKS endpoint has been unreachable for longer than plugins.sso_oidc JWKSMaxStale (default 12h) now fails SSO logins for that connection instead of continuing on the cached document. Raise JWKSMaxStale for an IdP with a poor availability record, noting that doing so widens the window in which a revoked key stays accepted.

## [0.43.0](https://github.com/yackey-labs/yauth/compare/v0.42.0...v0.43.0) (2026-08-15)


### ⚠ BREAKING CHANGES

* **auditexport,webhooks,passkey:** POST and PATCH on /api/auth/audit/destinations now reject a `config.hmac_secret` shorter than 32 characters with a 400. Requests that previously succeeded with a short signing key will fail; omit the key for an unsigned destination, or send `""` to stop signing. Existing destinations are unaffected until a request supplies a secret explicitly.
* **auth:** a stored Argon2id hash whose declared parameters fall outside t >= 1, p >= 1, 8*p <= m <= 2097152 KiB, salt >= 8 bytes and tag >= 16 bytes now fails to parse, and VerifyPassword returns ErrInvalidHash instead of verifying it. Hashes minted by yauth are unaffected: the package has emitted m=65536,t=1,p=4 with a 16-byte salt and a 32-byte tag since the Go port, and every one of those sits well inside the accepted range. A deployment that imported credentials from another Argon2 implementation with a tag shorter than 16 bytes, a salt shorter than 8, or m below 8*p will find those users unable to log in and must have them reset their password. That is the intended outcome — such a hash was being verified at a cost its own parameters misstate.
* **ssosaml:** inbound SAML assertions, Response signatures and HTTP-Redirect SLO signatures using SHA-1 (RSA-SHA1, DSA-SHA1, ECDSA-SHA1, or a SHA-1 reference digest) are now refused. Okta, Entra ID, Ping, OneLogin and Auth0 have defaulted to RSA-SHA256 for years and are unaffected, but ADFS 2.0 on Server 2008 R2, Shibboleth 2.x with legacy configuration and any crewjam-based IdP left on its default still sign with SHA-1 — and nothing in yauth's stored connection config records which IdP does what, so it cannot be determined from the database. Check each IdP's signing algorithm before upgrading and pre-set allow_sha1_signatures on any connection you cannot move; treat it as a migration deadline, not a setting. Refused logins are identifiable in the server log by the WARN row naming the flag.
* **oauth,ssooidc,auth:** on any deployment issuing Secure cookies, a federated login must now be completed in the browser that started it. Continuing a login in a different browser or on a different device — pasting the callback URL, or finishing the IdP leg on a phone — is refused with 400, which is precisely the attack. Native clients that fetch `/authorize` with their own HTTP client and then open an external browser are affected the same way.
* **middleware,oauth2server,yauth,yauthcfg:** a state-changing request that carries the session cookie and that the browser reports as cross-site is now answered 403 instead of being executed. Two knobs, both named verbatim in the refusal body so an operator holding nothing but a support ticket can find them: server.cross_site_writes.origins (defaults to server.cors.allowed_origins) and server.cross_site_writes.allow: true (turns the check off).
* **organizations,auth,scim,yauthcfg:** POST /organizations/{id}/members now answers 403 when the caller is not an install-wide admin and the organization holds no VERIFIED domain covering the target user's email address. Deployments affected are those driving the API as an org OWNER while holding the global role "user" — the classic realm-flat or single-tenant console, and provisioning scripts that create a user and immediately enrol them by id. A console whose operator account has the global role "admin" is exempt and sees no change. Three ways forward, in order of preference: verify the organization's email domain (POST /organizations/{id}/domains then .../verify); switch to POST /organizations/{id}/invitations, which the user accepts, and which can now be listed and revoked; or set plugins.organizations.allow_direct_member_enrollment: true, which restores the previous behaviour in full including the ability of any org admin to place a group name of their choosing into another user's id_token. Memberships already in the database are not touched by the upgrade; see the review query in docs/federation.md.
* **auditexport,domain:** PATCH/PUT on an audit-export destination now carries forward the config keys the API never echoes (hmac_secret, hec_token, api_key and every header.*) when the incoming config omits them; send the key with an empty string to clear it. Every other config key still replaces on omission. PUT shares the handler and is therefore carry-forward-shaped too.
* **plugin,middleware,admin,apikey,organizations,oauth2server,scim:** rows that were previously written to yauth_audit_log and delivered nowhere now reach every matching audit-export destination, and nine event types are new to the exported stream. A destination filtering on an allow-list of event types must be widened in one edit, and a receiver validating a CLOSED event-type enum will start rejecting. New to the stream: admin.user_created, admin.user_updated, admin.schedule_start, admin.sessions_revoked, apikey.created, apikey.revoked, apikey.rotated, user.unbanned, user.unsuspended — plus the previously table-only admin.*, oauth2.client.*, scim.* and session_*_mismatch rows.
* **admin,passwordpolicy,yauth:** POST {prefix}/admin/users now enforces email_password.password_policy on an admin-supplied password. An admin console or provisioning script that posts a fixed initial password weaker than the configured policy starts receiving 400 (or 422 when email_password.hibp_check is on and the password appears in a breach) where it previously received 201. The 400 body carries the same message /register already returns. Two smaller shape changes: an install with email_password enabled but no explicit password_policy inherits the min_password_length baseline (12 by default) on this route, where it previously had only the schema's 8-character floor; and the generated one-time password now contains a character from `!@#$%^*-_=+` and has a 20-char floor that grows with min_length, so anything pasting it into a URL or an unquoted shell command should quote it. The special-character set was chosen for shell and URL safety. Installs with email_password disabled are unaffected, and Go callers of admin.New() do not need to change: the new config parameter is variadic and the zero value preserves the previous behaviour exactly.
* **mailer/smtp,yauthcfg:** an SMTP config that sets only one of mailer.smtp.username_env / password_env, or that names an env var which is unset or empty, now fails at startup naming that variable instead of building a mailer that silently never issues AUTH. An install whose *_env is misspelled and has been sending unauthenticated to a permissive relay will FAIL TO BOOT on upgrade; set the variable, or remove both keys to send unauthenticated deliberately.
* **oauth2server,plugin,config,yauthcfg:** /oauth/token and /oauth/device/code now answer 429 after 150 requests per 60s from one client IP, and /oauth/introspect and /oauth/revoke after 300. These four endpoints previously had no ceiling at all. The most likely deployment to notice is an M2M fleet that exchanges client_credentials on every call instead of caching the access token from a single egress address, or an RFC 8628 device fleet — a device polls /oauth/token every plugins.oauth2_server.device_poll_interval seconds (default 5, so 12 requests a minute per device in flight) and every device behind one NAT shares the bucket. Raise rate_limit.oauth_token, or set `max: 0` for an explicit "no limit" if you meter these routes at the edge. Note also that the bucket keys on the client IP resolved under the trusted-proxy policy, so a deployment behind a reverse proxy that is not listed in trusted_proxies collapses every caller into one bucket. Fail-open is preserved: a rate-limit store outage returns a permissive result and cannot take the token endpoint down.
* **repo,pgxrepo,memrepo,conformance:** DeleteOrganization and DeleteGroup now delete rows they previously left behind. Any caller that relied on a group, its members, its client group assignments or its group-scoped client role assignments outliving the delete — including code that re-created an organization under the same id expecting its old auth policy or SSO connections to still be there — will see those rows gone. repo/conformance is exported API, so downstream repo.Repository implementations will fail the new org_cascade group until they cascade as well.
* **scim,emailpassword,magiclink,mailer:** a SCIM rename of a user's userName now retires that user's unused password resets, email verifications and unlock tokens, and unused magic links for both the old and the new address, in addition to the sessions and refresh tokens it already killed. Operators whose flow is "rename in the IdP, user clicks the reset link already in their inbox" will see that link 401. A SCIM write that does not change the login identity — the overwhelmingly common re-sync — still retires nothing.
* **passkey,repo:** a TOTP-enrolled user whose authenticator does not perform user verification now receives {require_mfa, pending_session_id} with no Set-Cookie from POST /passkey/login/finish, and completes at POST /mfa/verify, where they previously received a session in one leg. Clients that call this route must handle the require_mfa response shape that passkey.Config.SatisfiesMFA=false already documented. Users with no second factor enrolled, and users whose authenticator does perform user verification, are unaffected. Operators who need the old behaviour have no flag for it: satisfies_mfa=false only makes the step-up stricter.
* **oauth2server,oidc:** third-party private_key_jwt M2M clients must now send an `aud` naming this deployment (its issuer, its base URL, or the advertised token_endpoint), a non-empty `jti`, and an `exp` no more than 24h out, and must be registered with token_endpoint_auth_method private_key_jwt (or with none recorded). A public client can no longer authenticate by assertion at all. yauth ships no client_assertion producer of its own, so nothing in-tree breaks.
* **emailpassword,bearer,oauth2server,admin,repo:** repo.Repository implementations must make RevokeRefreshToken a compare-and-swap. Revoking an already-revoked row must change nothing and return yautherr.ErrNotFound instead of reporting success. This is the signal a rotation uses to detect that it lost a race and trip reuse detection; an implementation that stays idempotent silently forks the family. The repo/conformance suite now enforces it and the interface documents it. In-tree this affects pgxrepo and memrepo only — redisrepo does not implement RefreshTokenRepository.
* **webhooks,auditexport,oauth2server:** one outbound-egress guard, so an admin-chosen destination stops being an internal read primitive ([#108](https://github.com/yackey-labs/yauth/issues/108))
* **oauth,ssosaml:** plugins/oauth now sends a PKCE code_challenge on every authorization request and a code_verifier on every exchange, with no per-provider opt-out. An IdP that rejects unknown authorization parameters — rare, since RFC 7636 says extra parameters are ignored, but possible on old on-prem OIDC — will now fail where it previously succeeded.
* **apikey,middleware,passkey,mfa,organizations:** an org-scoped (service-account) API key can no longer pass RequireAdmin under any configuration. AllowAdminMachineCallers / plugins.admin.allow_machine_callers now means only "bearer tokens and user-scoped X-Api-Keys may administer"; automation that reached /admin/* with an org key must switch to a user-scoped key owned by an admin. The documented DCR admin_api_key federation path is unaffected — that key is user-scoped.
* **organizations,scim,auth:** removing a member from an organization, and deprovisioning a user over SCIM DELETE /Users/{id}, now also delete that user's group memberships within that organization. Three consequences for callers. Remove-and-re-add — a common way to change a role before the role endpoint existed — no longer preserves group memberships across the round trip; they must be re-added. Deployments using the realm-flat console pattern, where hidden `app-direct:` groups carry per-user app assignment, will see those direct app grants stripped on offboard; that is the correct semantics but it is a visible change. And a suspended or invited membership can no longer be added to a group: POST /organizations/{id}/groups/{gid}/members now answers 409 "user is not an active member of this organization" where it previously answered 204, and SCIM POST/PUT/PATCH /Groups silently skips such members while still returning their usual 201/200, so an IdP must re-push group membership after re-activating a user.
* **bearer,oauth2server:** a revoked OAuth2 access token no longer authenticates on any RequireAuth or RequireAdmin route; previously it kept working until it expired, and a deployment that (knowingly or not) relied on that grace window will see those callers start getting 401.
* **webhooks:** webhook deliveries are now DROPPED at the enqueue boundary when the dispatcher's job queue (WorkerCount * 8) is full, instead of blocking the emitting goroutine until a slot frees. A deployment that relied on the channel as durable backpressure — every emitted event eventually reaching a receiver, however slowly — no longer gets it; the trade is deliberate and is availability of authentication over at-least-once webhook delivery. Delivery FAILURES remain durable via the yauth_webhook_retries table; enqueue DROPS are not retried. Each drop emits a throttled `DROPPED delivery` warning through the host logger — alert on it, and raise WorkerCount for more headroom. `Dispatcher.Enqueue` keeps its signature but can now return the new exported `ErrQueueFull` on a healthy dispatcher, where previously a non-nil error meant shutdown only. `GET /webhooks` and `GET /webhooks/{id}/deliveries` now clamp a ?page= or ?per_page= above 1,000,000 to the default instead of accepting it (previously: a panic).
* **middleware,yauth,yauthcfg:** every response from ya.Router() now carries X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, X-Frame-Options: DENY and a Content-Security-Policy of "frame-ancestors 'none'; default-src 'none'; base-uri 'none'; form-action 'none'", unless the embedding application already set that header. Anything that framed a yauth route, or that relied on a yauth response carrying no CSP, will now be blocked by the browser. Set the header upstream of ya.Router(), use server.security_headers.override, or set server.security_headers.enabled: false. Strict-Transport-Security is NOT emitted by default: it requires both server.security_headers.hsts and a request that actually arrived over TLS.
* **mfa,bearer,lockout,emailpassword,events:** an account with an active lock is now refused on POST /mfa/verify and POST /token/mfa even with a correct code, and on the three MFA management routes once a step-up code has failed; callers that observed a 200 there will now see 429. Those three routes are additionally metered on the shared rate_limit.mfa_verify bucket, so a fat-fingered code now spends the same per-IP budget as MFA login — behind NAT that is 10/min for a whole office, and operators who feel it should raise rate_limit.mfa_verify. login.failed events for banned, suspended, staged, no-password, unknown-address and email-unverified outcomes now carry the events.MetaAdministrativeRefusal metadata key and no longer move the lockout counter; a deployment that relied on repeated hits against a disabled account tripping a lock now has only the per-IP /login limiter and the login.failed audit rows as anti-spray signal. Webhook subscribers of login.attempt will see one additional event per stepped-up login (audit rows are unaffected — auditableEvent records login.attempt only when Blocked).
* **scim:** SCIM PUT/PATCH may no longer repoint a userName into a domain the calling organization has not verified — cross-domain renames now return 409 uniqueness and require the domain to be added and verified first. A genuine rename now terminates every session and revokes every refresh token for that user. A non-boolean `active` other than "true"/"false" is now refused with 400 invalidValue where it previously answered 200 and did nothing, so Entra tenants that were silently failing to deprovision will surface new sync errors — the mapping was never working. userName is normalised to lower case before storage and lookup, so SCIM responses change case for accounts SCIM previously created with mixed case; consumers snapshotting those values should be checked. POST /Users no longer overwrites the role on a membership that already exists.
* **ssooidc,ssosaml:** a deployment where users self-served into an organization through a shared corporate IdP with no verified organization domain and no invitation now receives 403 from the SSO callback / SAML ACS until the organization verifies its email domain or an admin adds them via POST /organizations/{id}/members. Org-less global connections, first-time JIT provisioning, and SCIM-provisioned members (plugins/scim writes an active membership) are unaffected. The SSO callback's JSON user.email is now lowercased; display_name still carries the human-readable form.
* **magiclink,passkey,mfa,bearer:** suspended and staged accounts are now refused on /magic-link/verify, /passkey/login/finish, /mfa/verify and /token/mfa, and /mfa/verify additionally enforces the must-change-password gate. Callers that observed a 200 for these accounts will now see 403.
* **organizations,middleware:** a delegated OAuth2 access token is now refused with 403 and middleware.DelegatedCredentialDetail on every plugins/organizations route. Integrations that drove organization administration with a third-party access token must use a first-party credential or an org-scoped API key.
* **bearer,oauth2server:** a bearer access token now carries `token_use: "yauth_access"`, and a JWT presented to the bearer resolver, /oauth/introspect or /oauth/revoke must identify its kind. Tokens minted before the upgrade keep working for one AccessTTL. Anything that was relying on an id_token authenticating as its subject must exchange it for an access token.
